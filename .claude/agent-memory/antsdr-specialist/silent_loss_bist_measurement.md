Measured 2026-09-18 on our unit (`ip:192.168.1.10`), using `ad9361-phy` debug attrs `bist_tone`/`bist_prbs`/`loopback` (all confirmed present via `iio_attr -D`). `bist_tone` write format is `"<mode> <freq_Hz> <level_dB> <mask>"`; mode `2` = inject a digital NCO tone into the RX path **after the ADC** (bypasses analog front end/AGC/antenna entirely — a real scope limitation, not just a caveat to mention once). `TONE_FREQ` register floors at clk/32, so phase-based gap sizing is aliased modulo 32 samples — good for detecting *that* a gap occurred and a rough class, not exact size; corroborate large stalls via wall-clock refill duration instead.

**Method pitfall (re-derive-avoidance, not just a result):** an inline per-buffer phase-continuity analysis (numpy angle/diff/mod over 1,048,576 samples, ~67 ms) run in the *same thread* as the production-shape `buf.refill()/buf.read()` acquisition loop is itself slow enough (comparable to the 68–85 ms buffer period at these rates) to manufacture the very "silent loss" being measured — a 20s pilot with this bug showed 43% of buffer boundaries "lossy." Splitting into a producer thread (tight refill/read only) and a separate consumer thread for analysis (bounded queue, drop-oldest if it falls behind) fixed it — the same pilot then showed 0 events. **Any future ANTSDR diagnostic that shares a thread/process with the acquisition loop can fabricate this signature — always decouple.**

Results (10 min each, corrected two-thread design):
- 12.288 MS/s, idle host: 0 jump events (boundary or interior) over 7031/7031 buffers, throughput_ratio 0.9999 — clean.
- 13.44 MS/s, idle host: 0 jump events over 7690/7690 buffers, throughput_ratio 0.9999 — clean, corroborates the existing `MAX_SUSTAINED_RATE_HZ=13.44e6` production constant at sample granularity, not just aggregate ratio.
- 15.36 MS/s, idle host: throughput_ratio **0.50** (halved, not the "0.94-0.98 marginal" figure in older memory/notes — that older aggregate-ratio number understates how broken this rate actually is), 98% of refills abnormally long, ~2.1M phase-discontinuity events **overwhelmingly interior** (99.99% mid-buffer, not boundary-aligned) — i.e. a continuous fine-grained drizzle of small discontinuities throughout every buffer, plus separate macroscopic refill stalls. **Do not use 15.36 MS/s; treat as badly broken, not marginal.**
- 12.288 MS/s with a same-process GIL-bound "CPU load" (12 `threading.Thread` busy-loops, not real multi-core contention): throughput_ratio dropped to 0.41 with a similar interior-corruption pattern to the broken 15.36 MS/s case — i.e. a CPU-heavy stage *sharing the acquisition process/GIL* (like the real backend's `StreamAssembler` consumer) can push even a clean rate into the same broken regime. This result's exact jump/interior counts have a ~10% internal-consistency discrepancy (a benign counter race in the diagnostic script when its own analysis thread falls far behind — `queue_drops` nonzero) — treat as order-of-magnitude only, not exact.
- A follow-up run with genuine external-process load (12 separate `subprocess.Popen` workers, not GIL-bound) was started but killed by the harness's own low-memory protection before completing (system-wide, not attributable to this run's footprint from what was observable). **Not retried per explicit instruction. Genuine multi-core host contention at 12.288/13.44 MS/s remains unmeasured — flag as an open item, do not assume "probably fine" from the clean idle-host results.**

Device left reset: `bist_tone`/`bist_prbs`/`loopback` confirmed back to `0`/disabled; a follow-up normal capture read `rssi=96.75 dB` with a structured (non-flat) ambient spectrum, confirming ordinary receive mode restored (the harness-killed run never reached its own cleanup, so this was verified explicitly rather than assumed).

**Why:** turns the previous only-available silent-loss proxy (`stream_rate_ratio`, ~0.25%-resolution aggregate) into a directly-measured, sample-level finding, and answers the standing "does silent loss cluster at buffer boundaries or is it arbitrary" question the architect needed for the abstraction design.

**How to apply:** keep the production ceiling recommendation at 13.44 MS/s (unchanged, now more strongly evidenced) — see [[firmware-streaming-ceiling]] and [[device-facts-e200]]. Do not plan around 15.36 MS/s "sometimes working." Flag to the architect that a CPU-heavy consumer stage sharing the acquisition process is a credible degradation path even at 12.288/13.44 MS/s, worth a real multi-core-contention test before that risk is called closed. Full method, tables, and caveats are in `research/briefs/antsdr-e200.md` §14 — read that fresh, this memory is a pointer/summary.
